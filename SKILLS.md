# OlmoEarth Agent Skills Catalog

Detailed spec for the 13 skills the agent ships with. Each skill is an [agentskills.io](https://agentskills.io)-spec package (`SKILL.md` + frontmatter + optional `scripts/`, `references/`, `assets/`, `skill-card.md`, `skill.oms.sig`).

`PLAN.md` is the runtime contract (tools, dataclasses, operational rules). This file is the *skill-layer* contract: what each skill does, why, the tools it composes (from `PLAN.md` §1 or skill-local), and the academic / engineering references that justify it.

**Status:** 13 skills, all implemented in this repo. By default the agent is the Studio run loop and a verification layer: which windows to review, which to label, how wrong a map is and where it can be trusted (#18, through `olmoearth-inferencex`, for a map that carries scores: a Studio result whose band is a `[0, 1]` score or a regression band given a threshold, a Studio class map with top-k scores, or a direct model run's scores; a Studio class map without top-k scores gets its error rate and per-class accuracy from labels, but no review set and no certified zone), and which of two maps of one time is more accurate (#18's two-map route, class maps included: labels where they differ), with the comparison tools of #4, #5 and #9. The foundational Studio tools include `olmoearth_studio_label_inventory`, which counts the Studio annotations a model's training selector selects now (no error rate: Studio records no random design for them). Ten tools are opt-in ([Opt-in tools](#opt-in-tools)): they leave the default registry, stay in the code, and come back with `OLMOEARTH_OPT_IN_TOOLS=1`. History: v1.0 shipped the originals on 2026-05-31; the `olmoearth_automate` facet was added post-1.0, #17 `olmoearth-rslearn` post-1.2 (a vendored "operate rslearn" SKILL.md plus four torch-free tools), #18 `olmoearth-review-set` post-1.4 (label-free error ranking from the model's own margin, the half of the uncertainty question #9 cannot reach), and in the unreleased version (`CHANGELOG.md`, Unreleased) the default registry is the verification layer, and five skills outside inference examination (#6, #8, #10, #15 and #16) were removed. A JEPA latent-change detector lives in the separate repo [`2imi9/olmoearth-jepa-change`](https://github.com/2imi9/olmoearth-jepa-change); it is not connected to this agent. See `CHANGELOG.md`.

## Prep

### 1. `olmoearth-data-prep`

**Upstream:** the single vendored [`olmoearth-data-prep`](https://github.com/2imi9/OlmoEarth-Skills/tree/main/skills/olmoearth-data-prep) package (see the [`SKILL.md`](https://raw.githubusercontent.com/2imi9/OlmoEarth-Skills/main/skills/olmoearth-data-prep/SKILL.md) and `scripts/audit.py`, `scripts/write_config.py`). It covers both halves of label prep — Studio import and rslearn config — which earlier catalog versions split into two entries.

**In:** labels as GeoJSON / CSV / Shapefile (+ optional AOIs).
**Out:** a Studio-importable file AND/OR an `rslearn` `dataset.json` + Lightning YAML.

**What.** *Studio import:* `sample_category` schema enforcement, sharding at 10K records, dual file extension to bypass Windows MIME rejection, multi-metric file split when more than one numeric column is present. *rslearn config:* `oe_labels` schema, single-layer 3-bandset (AWF-style) or per-month production layout, the `es_label` rename, watershed AOIs from NLDI / HUC-12, and a 7-criteria audit before training starts. Recognizes all three label schemas (`sample_category` / `es_label` / `oe_labels.{key}`).

**Why.** Onboarding friction is the most repeated dropoff point for case providers. Studio uploads break silently: Windows rejects `.geojson` as `application/octet-stream`, and uploads above 10K records hit the 1-hour timeout. Config friction is likewise a documented barrier to operationalizing geospatial foundation models ([WorldCereal deployment lessons, arXiv:2508.00858](https://arxiv.org/abs/2508.00858), preprint): the `es_label` rename trap and layout confusion cause silent failures that only show up after a multi-hour training run.

**Tools composed.**
- `olmoearth_load_skill` (pulls the vendored `SKILL.md` into context on demand).
- Upstream skill-local: `validate_studio_mime`, `shard_at_10k`, `split_multi_metric`, `write_rslearn_config`, `audit_7_criteria`, `rename_es_label`; `eo.window_tile` / `olmoearth.resolve_to_aoi` (`PLAN.md` §1).

## Configure

### 2. `olmoearth-studio-job-config`

**Upstream:** [`2imi9/OlmoEarth-Skills/skills/olmoearth-studio-job-config`](https://github.com/2imi9/OlmoEarth-Skills/tree/main/skills/olmoearth-studio-job-config), moved as-is into `src/olmoearth_agent/skills/packages/`.

**In:** task description.
**Out:** Studio "new model" wizard answers.

**What.** Walks Studio's "new model" wizard end to end: model name, model type (per-pixel / window / detection / embeddings, with the wizard's fine-tuned-vs-embeddings framing), foundation model (Nano / Tiny / Base), label field, training data (full vs a proportion), data split (Spatial recommended vs a metadata field), temporal context (period vs single-moment-with-context vs single-moment), image sources (S2 alone vs +S1), surrounding area (160 / 320 / **640 default** / 1280 m). 14 verified presets (crop / mangrove / land cover / soil moisture / biomass / vessel / solar / oil slick / flood / drought / burn scar / embeddings) plus a cross-field validator. Studio trains on Ai2's compute — the skill never asks about the user's own hardware and never reroutes Studio model-creation to local training.

**Why.** Cross-field traps exist: detection with a small patch fails silently, Landsat is not yet selectable as a source, embeddings mode is incompatible with the label-dependent steps, random splits leak spatial neighbors. Researchers without OlmoEarth-specific intuition iterate on a misconfigured wizard for days. The validator catches the trap before the model is created.

**Tools composed.**
- `olmoearth_load_skill`; skill-local: `studio_job_validate`, `apply_preset`, `cross_field_check`.

### 3. `olmoearth-embeddings`

**Upstream:** [`2imi9/OlmoEarth-Skills/skills/olmoearth-embeddings`](https://github.com/2imi9/OlmoEarth-Skills/tree/main/skills/olmoearth-embeddings); grounded in the AWF Kenya tutorial's accuracy/time/VRAM table. Handles the small-dataset (<100 samples), limited-compute (T4 / Colab), similarity-search, and "no labels yet" cases.

**In:** task profile (label volume, class balance, target VRAM, target latency); or a free-form `task` / a Hugging Face `hf_dataset` id for the one-call path.
**Out:** an embeddings-vs-fine-tune decision + either a runnable `.ipynb` (the guidance path) or a ready config (the one-call path).

**What.** One embeddings-vs-fine-tune decision, offered two ways. **Guidance + notebook (vendored):** explains the decision grounded in the fine-tuned OlmoEarth benchmark table and emits a parameterized notebook that extracts Nano / Tiny / Base / Large embeddings and trains kNN + linear-probe heads for the **user** to run. Ai2 now publishes precomputed [OlmoEarth v1.3 embeddings](https://source.coop/olmoearth/olmoearth-v1-3-embeddings) on Source Cooperative: one 128-dimensional vector per 10 m pixel per year, from a different model than the notebook's Nano / Tiny / Base / Large. They replace extracting embeddings yourself for an annual task in an area and year they cover; a task that needs dates within a year still needs the notebook. **One-call automation (in-repo `olmoearth_automate`, opt-in):** applies the same precedence rules programmatically — a faithful port of the vendored `recommend.decide`, kept in sync — and proposes an actionable config (model size, classifier head, an embeddings-notebook command, a fine-tune schedule, and a hand-off to skill #2 `olmoearth-studio-job-config`); given a Hugging Face dataset id it reads the row count + ClassLabel classes from the public datasets-server to fill its inputs. Inputs are task metadata only (no geometry), so results are provenance-safe.

**Why.** Embeddings-vs-fine-tune is the most frequent decision point in EO foundation model use. Practitioners without empirical guidance over-fit Large models on small samples or under-use embeddings when they would have sufficed. The measured accuracy / time / VRAM tradeoffs make the choice visible and actionable — a direct counter to AlphaEarth being shipped as annualized embeddings only (Ai2's precomputed v1.3 embeddings are annual too, so the notebook stays for a task whose signal falls within a year). **No fabrication:** the one-call path reports `ask_for` when key inputs are missing rather than guessing, and never invents dataset stats.

**Tools composed.**
- `olmoearth_load_skill` (the vendored guidance + notebook generator) and, opt-in, `olmoearth_automate` (the in-repo one-call decision + config + optional HF-dataset introspection).
- Logic in `analysis/automate.py` (decision port + `propose_config` + `fetch_hf_dataset_profile`); the generated notebook is meant for the **user** to run (it needs the geospatial/GPU stack). No tool fetches embeddings.

## Run

### 4. `olmoearth-predict`

**In:** Studio project + area + model_id + time range + config.
**Out:** `PredictionRef`, status, and result tiles / vectors / metrics.

**What.** Submit a prediction (`POST /predictions`), poll progress (`GET /predictions/{id}`), and fetch results (tiles / vectors / metrics). Pixel-value at a point (`/pixel-value`) is exposed as the `olmoearth_pixel_value` tool (the model's output sampled at one user-supplied lon/lat, not an interpolated read and not validated truth).

**Why.** The Studio API is async with a 5-state status enum (`pending / running / completed / failed / cancelled`) and a `download_token` flow. Without a wrapper, every case study re-implements the polling loop, retry on result-creation failures, and the tile-vs-raw-output decision. This is the core run primitive every other skill depends on.

**Tools composed.**
- `olmoearth_search_predictions`, `olmoearth_submit_prediction`, `olmoearth_get_prediction`, `olmoearth_fetch_results`, `olmoearth_get_prediction_result` (wrapping `PLAN.md` §1 submit / poll / fetch_results). Studio filters the predictions and results searches itself (checked live on 31 October 2026), and `olmoearth_fetch_results` returns each result's declared outputs, period and `file_formats`. `olmoearth_submit_prediction` takes an optional `probability_top_k`, sent as Studio's `probability_output`: a segmentation model's class map then carries its top-k class scores, which #18 ranks (from the spec; unverified with a read-only key). With `OLMOEARTH_READ_ONLY=1` (a read-only Studio key), `olmoearth_submit_prediction` and `olmoearth_create_project` are left out, and the capability card says why. Drawing an area (`olmoearth_request_aoi`) stays; the web UI answers a refused save with HTTP 403.
- `olmoearth_studio_label_inventory` (foundational, read-only): counts the Studio annotations a model's training selector selects now, or a project's, by status, geometry, split and class. Studio records no random design for them, so they give no error rate; the next step is #18's `olmoearth_plan_label_sample`.
- `olmoearth_pixel_value`: reads one result's model output at a single lon/lat the user supplies (`raw_value` for a regression layer, the class for a categorical one), or reports `available: false` off-raster. The user provides the point, so echoing it back is `PLAN.md` §3.1-compliant.
- `olmoearth_compare_results`: the one tool for "how do these Studio results differ?", with no ground truth. It takes 2-8 result ids, samples every raster on one grid of windows (pointwise `pixel-value`) over their shared extent, and reads the samples in one of four modes. `pair` (two results): mean / mean-absolute difference, RMSE, correlation, and an agreement fraction (regression) or class agreement (classification); `kind` frames it as `cross_model` (two models: how much they *agree* -- divergence, not accuracy) or `temporal` (one model, earlier vs later date: net *change*, later minus earlier, ordered by the predictions' dates when known). `group` (2-6 models): a **pairwise matrix**, an **ensemble consensus** (fraction of cells where *all* models agree within tolerance / pick the same class, mean spread, the most divergent pair), and the most-contested cells. `series` and `ensemble` are skill #5's shift trace and skill #9's disagreement signal. The default `auto` mode picks pair, series or group from the results' models and dates. Studio returns no-data as a value (e.g. `-1` on a `[0, 1]` score), so every mode drops a value that is missing or NaN, equals the model's `nodata_value`, or lies outside the band's declared range, and reports `n_nodata_dropped`; results of different properties are refused before any sampling (a pair or a group may pass `allow_different_properties`, and then only correlations are meaningful). Every correlation returned is also a `correlation` fact with its 95% interval by Fisher's z, and the result forbids reading a place from it (it is pooled over every cell) or, when the interval holds both no relation and a moderate one, saying whether the maps co-vary at all; below 50 cells a next step names a denser `grid`. Cells are named by grid `(row, col)` and index, never by coordinates (`PLAN.md` §3.1). The returned `narration` (labels + headline) and the in-chat card / difference-scan captions adapt to the mode and kind. Each result adds grid^2 slow Studio `pixel-value` calls, so grids are small and capped per mode. This is the numeric counterpart to the side-by-side raster preview; for accuracy against labels use skill #7 `olmoearth-evaluate`, for how wrong one map is, skill #18, and for which of two maps of one time is more accurate, #18's two-map route (`olmoearth_plan_label_sample` with `design='disagreement'` samples the two results with this tool's pair sampler).

**AOI input (draw-in-chat).** `submit_prediction` needs an `area_id`, which it sends to Studio as `target_area_ids`. Rather than ask the user to type a bbox, the agent calls the foundational `olmoearth_request_aoi` tool, which surfaces an interactive map in the web UI; the user **draws** a rectangle or polygon, it is stored as a Studio area (`POST /areas` -> `area_id`), and its `area_id` + bounding box are fed back on the next turn.

**First skill to ship.** Foundation that #5 and #9 reuse.

### 5. `olmoearth-change-detection`

**In:** 3-8 Studio result ids of one model over the same area (refuses 2 as a series).
**Out:** per-step statistics, per-point trajectories and calibrated shift sizes across the dates.

**Result-level shift tracing (the default).** `olmoearth_compare_results` in series mode (`mode="series"`, or `auto` when the results are one model on three or more dates) is the tool for change over time: give it 3-8 result ids of ONE model over the same area and it discovers each result's date itself (via its prediction's `start_time`), orders the series chronologically (falling back loudly to given-order when a date is missing — a silently wrong order would flip every shift sign), samples all results on one shared grid, and returns per-step stats (Pearson correlation / mean delta / agreement, the "pixel correlation" trace), per-point trajectories (net change, OLS slope, largest step + its dates, top shifted points), and shift sizes calibrated to the field's value range — `value_range` from the project's annotation form when the user knows it, else the observed range, each labeled as such (`calibration.source`). Categorical results get class-transition counts instead ("legend" reading of a shift). Honest framing throughout: estimate movement between run dates, not verified ground change, not accuracy. Cost-capped like all sampling tools (results x grid^2 live pixel-value calls).

**Why three dates.** Two-date diffs hide gradual drift and cannot tell a steady trend from a reversal, and annualized embedding products structurally cannot capture intra-annual signals such as cover-crop transitions, flood peaks, and harvest timing (consistent with [Ma et al. arXiv:2601.00857](https://arxiv.org/abs/2601.00857), preprint).

**Trajectory of the caller's own values (opt-in).** `olmoearth_change_detect` turns a dated series of per-date values the caller gives into trajectory metrics: step deltas, net change, the largest-change interval, a reversal count, and a trend label. It refuses fewer than 3 dates, because a 2-date diff cannot tell a steady trend from a flood that peaked then receded. It is opt-in (`OLMOEARTH_OPT_IN_TOOLS=1`): series mode above reads the dated results themselves, so it superseded this tool.

**Not connected: the JEPA latent-change detector.** A change detector on frozen OlmoEarth embeddings (the residual of predicting the time-2 embedding from time-1) lives in the separate repo [`2imi9/olmoearth-jepa-change`](https://github.com/2imi9/olmoearth-jepa-change). No tool of this agent calls it, and connecting it is not planned: label-free change maps are what Google's and Ai2's own tools already make, and this agent verifies maps instead of making them.

## Analyze

### 7. `olmoearth-evaluate`

**In:** the user's ground-truth labels and the map's classes at the same points; *(opt-in)* labelled points and prediction points.
**Out:** per-class metrics; *(opt-in)* spatial-block CV inflation and NNDM-LOO results.

**What.** Accuracy, per-class precision / recall / F1 / IoU against labels the user gives. Opt-in (`OLMOEARTH_OPT_IN_TOOLS=1`; training-side checks, run outside Studio): spatial-block cross-validation and nearest-neighbor-distance-matching LOO-CV. A Studio user who wants a map's error rate with an interval uses #18's design-based estimation, which needs no model training.

**Why.** [Ploton et al. (Nat. Commun. 11:4540, 2020)](https://www.nature.com/articles/s41467-020-18321-y) showed that standard random CV can report strong R2 on models with near-zero spatial predictive skill. [Meyer & Pebesma (MEE 12:1620, 2021)](https://besjournals.onlinelibrary.wiley.com/doi/10.1111/2041-210X.13650) formalized this. Without spatial CV, an accuracy quoted for a model you train yourself risks being inflated. This is the most-cited methodological pain in EO ML literature. These checks apply to a model you train yourself; for a Studio map's error rate the agent uses #18's design-based estimate, which needs no spatial CV.

**Tools composed.**
- `olmoearth_cv_inflation_check` (opt-in): random-vs-spatial-block test-to-train distance ratio (the fast "is my accuracy inflated?" check).
- `olmoearth_nndm_cv` (opt-in): NNDM Leave-One-Out folds for an unbiased estimate over the actual prediction area, a faithful pure-Python port of R [CAST](https://github.com/HannaMeyer/CAST)'s `nndm` ([Mila et al., MEE 13:1304, 2022](https://besjournals.onlinelibrary.wiley.com/doi/10.1111/2041-210X.13851)) -- verified against the reference algorithm (exact hand-trace + the `predpoints==trainpoints` invariant).
- `olmoearth_classification_metrics`: accuracy + per-class precision / recall / F1 / IoU.

### 9. `olmoearth-uncertainty`

**In:** *(confidence)* two or more prediction results over a shared area; *(OOD, opt-in)* training-data feature vectors + the AOI points to assess.
**Out:** *(confidence)* per-point + aggregate ensemble-disagreement stats; *(OOD, opt-in)* a DI-weighted out-of-distribution flag per point.

**What.** Two complementary uncertainty signals. *Ensemble-disagreement confidence:* samples two or more **distinct** prediction results on a shared-extent grid and treats the per-point values as ensemble members, returning per-point dispersion (std / coefficient-of-variation / range for regression; majority class / vote fractions / normalized Shannon entropy / margin for categorical) folded into a confidence in [0,1]. The variance is real (distinct results), never a fake re-read of one deterministic result, and it is **epistemic uncertainty — model self-consistency, not a calibrated correctness probability.** *Area of Applicability (opt-in):* a Meyer-Pebesma Dissimilarity-Index-weighted out-of-distribution flag that warns when an AOI lies outside the trained feature space. With `OLMOEARTH_OPT_IN_TOOLS=1`, use them together: trust a prediction most when it is both inside the AOA and low-dispersion. **Scope, and why #18 exists.** Neither signal ranks *which windows are wrong*: upstream ([`2imi9/olmoearth_inferenceX-record`](https://github.com/2imi9/olmoearth_inferenceX-record)) measured ensemble disagreement and feature-space typicality against the model's own top-1-minus-top-2 margin on expert-labelled testbeds and neither won. That is not a defect here — for a Studio class map without top-k scores, `pixel-value` returns only `raw_value`/`classification`, never probabilities or logits, so the margin is not computable and ensemble disagreement is the only signal reachable. When per-class scores do exist (a direct run's, or the top-k class scores of a prediction submitted with `probability_output`), route the error-ranking question to #18 `olmoearth-review-set`.

**Why.** Softmax confidence is not OOD detection. Meyer & Pebesma's [Area of Applicability framework](https://besjournals.onlinelibrary.wiley.com/doi/10.1111/2041-210X.13650) (R [`CAST`](https://cran.r-project.org/package=CAST) package, on CRAN since 2018) is implemented across multiple peer-reviewed methods papers but absent from every EO foundation model platform. AlphaEarth's documented transfer failure under domain shift is exactly what AOA would have flagged.

**Tools composed.**
- `olmoearth_area_of_applicability` (opt-in: the AOA / OOD flag over caller-supplied feature vectors, which no tool produces, and measured not to rank errors better than the margin) and `olmoearth_compare_results` with `mode="ensemble"` (samples >= 2 results via `olmoearth.pixel_value`, `PLAN.md` §1, into an ensemble-disagreement confidence map, each cell named by grid `(row, col)`).
- Logic in `analysis/uncertainty.py`: `area_of_applicability` + `ood_flag` (AOA), and `prediction_confidence` (the pure dispersion / entropy statistics).

### 13. `olmoearth-provenance`

**In:** every API call (transparent wrap).
**Out:** manifest + single-command replay script + the verification calls with their seeds.

**What.** Manifest of `prediction_id`, `model_id`, dataset hashes, time window, parameters, tile dates. Emits a single-command replay script so the case can be re-run by a third party. The verification calls (`olmoearth_plan_label_sample`, `olmoearth_estimate_map_error`, `olmoearth_certify_zone`, `olmoearth_write_certificate`, `olmoearth_verify_certificate`) are kept whole (`ProvenanceLog.verification`). `olmoearth_provenance_summary` lists each one with what repeats its sample (`verification_calls`): the design, the budget, the seed (for a plan drawn with `seed_from_map`, the one taken from the map, listed with `seed_from_map=True`: the plan is drawn again with that flag and its alpha, delta and rule, not with the seed), the maps or scores file it read, the design file and labels, the zone's alpha, delta and rule, and a certificate's date, path, the map copy checked against, the window asked about and whether it verified. [Kedron & Holler (Remote Sensing 14:5471, 2022)](https://doi.org/10.3390/rs14215471) call for benchmark datasets to test replicability in remote sensing specifically. - Hooks into every `PLAN.md` §1 `olmoearth.*` call via `provenance_middleware` (added to `PLAN.md` §3 as Rule 13).
- Skill-local: `manifest_write`, `replay_script_emit`, `dataset_hash`.

**Operational rule.** Adds rule 13 to `PLAN.md` §3: *every Studio API call emits a manifest entry; sessions that disable provenance refuse to call `save_view`.*

### 14. `olmoearth-case-narrative`

**In:** `tile_urls` + provenance manifest + the request's recorded verification calls.
**Out:** stakeholder writeup with live tiles + freshness gate + a "How accurate is this map" section.

**What.** Stakeholder writeup with embedded live map tiles, citations to dataset hashes, and a freshness gate that refuses to render stale tiles past a configurable window.

**How accurate is this map.** The report reads the verification results the way it reads provenance: from the log of the same request (`ProvenanceLog.verification`), never from figures the model types. A request is one run of the agent. On the web UI each message is a request of its own, with a fresh log, so an estimate made in an earlier message is not in it: the report states it only when `olmoearth_estimate_map_error` is called again in this request, with that `design_path` and its labels. The report states, as the tools returned them:
- each error rate (`olmoearth_estimate_map_error`), with the map it is of (named by its plan in the request), every interval it has, each named with its method and level: valid at every sample size; the design's own, exact or by the union bound; nominal and approximate where the package's method is a Wilson interval (the confidence and proportional designs; the package's `VALID_NOTE` gives the coverage it fell to); the number of labels, the design and its seed; the per-class ranking (`weakest_classes`);
- windows labelled without a design (`window_indices`): the interval they would earn as a simple random sample, which nothing establishes, that the package checked only that they are not a review set, and its flag when they come from the confident end of the map;
- each certified zone (`olmoearth_certify_zone`), with what alpha bounds and olmoearth-inferencex's `ISSUED_NOTE` on what delta counts, word for word. A zone call that changed its alpha, delta or rule after an earlier zone call on the same design file, or its labels after an earlier call graded others there, is a second look the guarantee does not cover: it is stated as such, never as certified;
- each certificate written (`olmoearth_write_certificate`), with the package's statement, the zone's `ISSUED_NOTE` and `ISSUERS_WORD` (what is taken on the issuer's word), word for word, since a certificate restates its zone and never replaces that note, and the tool's summary of what a certificate proves (from the package's Usage, "certificate and verify"); or why none was written; with the whole-map estimate from its labels, as the zone states it; and each certificate checked (`olmoearth_verify_certificate`): verified, with the statement certify gives again, or each failed check in the package's words, against the map read (said when it is the path the certificate names, or `map_path` is that same file, not a copy), and the window asked about;
- each which-map verdict, with the exact sign test or the interval it rests on;
- labels changed on a design file after a result was seen (other labels given inline, another whole-map figure, or another digest of the labels, `labels_sha256`, which the zone and the certificate return);
- the tool's `must_state` limits and the package's notes: an estimate's `warning` (beside the interval valid at every sample size, named as of the interval the design earns), `bounds_note`, `condition_note` and `valid_note` (and the tool's `class_map_note` for a class map); the per-class table's `warning` and `valid_note` (its intervals hold one by one, not jointly) and the `warning` of each class `weakest_classes` names; the zone's `note` (its rule); the which-map grading's `note` and `verdict_note`; and the package's `scope` note up to its first sentence with a percent figure or a command-line option (the rest gives another map's figures, exp88).

A plan still awaiting labels is listed with its design and seed. Without an estimated error rate the section says plainly that none was estimated in the request, and names the tools that estimate one; when `olmoearth_classification_metrics` (#7) computed accuracy against the caller's labels, it says that is agreement with those labels, not the map's error rate from a planned sample. The result then requires the answer to say so (`must_state`) and forbids any accuracy figure for the map (`accuracy_not_measured`). The answer checks read that id without the hedges that excuse a plan's `error_rate_without_labels` ("from 300 labelled windows" names a source the request does not hold), and not at all once the run holds a measured estimate or a successful `olmoearth_classification_metrics` call; nor for a which-map grading's difference in accuracy, or, on the web UI, a figure an earlier message stated. A title or result typed with an accuracy figure is refused (the error names where, not the figure), so the report never shows a figure no tool returned. The report's Markdown is no source of numbers for the answer's number check (`not_a_source`): it renders the title and results the model typed.

**Why.** Practitioners working under operational timelines often need to ship a working solution rather than an optimal one ([WorldCereal lessons, arXiv:2508.00858](https://arxiv.org/abs/2508.00858), preprint). NGO leadership, journalists, and policymakers need outputs tied to map tiles and policy briefs, not Jupyter notebooks. Freshness gating prevents stale-tile reports during disaster response when conditions change within hours.

**Tools composed.**
- Skill #13 (`olmoearth-provenance`) for manifest read, and the verification calls it keeps.
- Skill #18's estimation and certificate tools (`olmoearth_estimate_map_error`, `olmoearth_certify_zone`, `olmoearth_write_certificate`, `olmoearth_verify_certificate`) for the accuracy section.
- `olmoearth.fetch_results` for tile URLs.
- Skill-local: `freshness_gate`, `narrative_template`, `tile_embed`.

### 17. `olmoearth-rslearn`

**In:** a plain-language research goal (+ optional `task`, `num_classes`, `label_range`, `sensor`, `cloudy`, `temporal`, `num_samples`, `model_size`); or, for validation, a parsed dataset `config.json` and/or model `model.yaml`.
**Out:** for *recommend*, a complete explained setup (task + data layout + `encoder -> decoder -> head` + task knobs + fine-tune schedule, each with a one-line *why*, and `ask_for` for missing inputs); for *validate*, `{ok, errors, warnings, checks}`.

**Opt-in tools** (`OLMOEARTH_OPT_IN_TOOLS=1`): the four tools serve model training outside Studio; the vendored SKILL.md still loads by default.

**What.** [`rslearn`](https://github.com/allenai/rslearn) (AI2, Apache-2.0) is the data + training engine **under** OlmoEarth. The vendored `olmoearth-rslearn` SKILL.md teaches *running* it (the 4-stage `add_windows -> prepare -> ingest -> materialize` pipeline, then `model fit`/`predict`). On top of that, four **torch-free** in-repo tools (opt-in) let a domain scientist who does **not** know rslearn still set up a correct experiment. `olmoearth_rslearn_recommend` maps a goal to the right rslearn task (segmentation / per-pixel-regression / detection / classification / regression), a sensible OlmoEarth `encoder -> decoder -> head` composition with the channel contract spelled out, the data layout (`data_source` + `space_mode` + `compositing_method` + bands), the task knobs (metrics / loss / `nodata_value` / `scale_factor` from the label range), and a freeze->unfreeze schedule. `olmoearth_rslearn_validate` catches the errors rslearn only surfaces hours into a run: encoder embedding-dim vs decoder `in_channels`, decoder `out_channels` vs `num_classes`, task vs label-type (Segmentation/per-pixel need a raster target; Classification/Detection/Regression need vector), model `inputs.layers`/bands that aren't in the dataset, bad `dtype`/`sort_by`, and the Faster R-CNN background-class **+1** quirk. `olmoearth_rslearn_compose` then emits a complete, valid finetune `model.yaml` (single-source, or multi-source fusion via `modalities` + `fusion`), and `olmoearth_rslearn_diagnose` turns a failing `prepare`/`ingest`/`materialize` run into plain-English fixes.

**Why.** rslearn's config + `encoder->decoder->head` framework is a wall for the domain scientists OlmoEarth is for — they have a research question and labels, not ML-engineering fluency. These tools turn "read the docs and hand-write YAML" into "describe the goal, get a correct + explained setup, and have it checked before a multi-hour GPU run." **Torch-free by construction:** importing rslearn would pull torch (excluded from this agent), so the logic mirrors rslearn's facts (tasks, model sizes, config enums) as plain data in `analysis/rslearn_advisor.py`, verified against the rslearn repo with a version pointer — heavy training stays **out of this process**, run by the user. Pure metadata in/out (no geometry, no network) → provenance-safe.

**Tools composed.**
- `olmoearth_load_skill` (load the vendored "operate rslearn" SKILL.md for the pipeline + `fit`/`predict`).
- Opt-in: `olmoearth_rslearn_recommend` (goal → explained setup; with 2+ `modalities`, also a pre/mid/post **fusion** recommendation), `olmoearth_rslearn_validate` (catch shape / label-type / band errors before training), `olmoearth_rslearn_compose` (emit a full valid finetune `model.yaml`; with 2+ `modalities` it emits a **multi-source fusion** config — `mid` = one OlmoEarth encoder fed every modality and fused internally via cross-modal attention, the OlmoEarth-native default; `cross_attention` / `pre` / `post` return grounded guidance), and `olmoearth_rslearn_diagnose` (parse a failing `prepare`/`ingest`/`materialize` run → plain-English fixes). Logic in `analysis/rslearn_advisor.py`; rslearn's tasks/models/config schemas — including the multi-input modalities (`OlmoEarth.MODALITY_NAMES`) and `CrossAttentionFusionExtractor` — mirrored as torch-free data, verified against the repo.

### 18. `olmoearth-review-set`

**In:** per-window model scores (`n_windows x n_classes` logits or probabilities), a direct model run's directory (a scores raster and its `manifest.json`, or the `scores_<EPSG>.tif` and `olmoearth_output.json` that `oe-inferencex from-olmoearth` writes), or a Studio `result_id` whose band is a binary score in `[0, 1]` or a class map with top-k scores (sampled on a grid, or read from its native-resolution files by `olmoearth_scores_from_studio`); a review budget, optionally a `[rows, cols]` grid; for grading, a candidate signal + a 0/1 error indicator (+ optional baseline, no-model control, group ids); for estimation, a label budget and then the reviewer's 0/1 labels; for which of two maps is more accurate, two maps of one time (two Studio results, or two scores files of one window grid), a label budget, and then the class seen in each planned window.
**Out:** the ordered review set at that budget (window index / (row, col) / predicted class / margin / boundary count; a review set listed short is saved whole to a CSV at `review_list_path`, without coordinates), the margin summary, the attainable-ceiling arithmetic, one `evidence_scope` sentence (what was measured, on what, and whether it covers this case; the full evidence text is saved to a file named by `evidence_detail_path`), and the output contract (`facts` such as `margin_ratio`, `review_set_classes` (every window of the review set by predicted class, not only the listed ones) and `list_file` (a sentence naming the file a list was written to), `must_state` with at most three limits of at most 25 words, `forbidden_claims`, among them `margin_as_error_probability`: a margin orders a review, it is not how likely a window is wrong); for a comparison of two inferences, directed `class_changes` and undirected `class_pairs`, which side is more confident on what share, a row- and column-band `spatial` breakdown (`concentration`: row band 0's share, called the northmost only when the scores are georeferenced, and the band holding the most), the share of differing windows on map A's predicted boundaries (`boundary_share`, which does not show whether whole regions flip), the 8-connected patches the differing windows form on the grid as plain counts (`n_patches`, `largest_patches`, `differing_in_patches_ge_100`, and `differing_interior`: the windows whose every neighbour on the grid differs too, stated by the `contiguity` fact, which reads them only by that interior share, since a long strip along a class edge also forms a large patch; `mostly_edges` forbids "mostly edges" while at least half of the differing windows are interior, in every comparison of the run that lists it), for maps of different or overlapping times what they do not get (`not_for_these_maps`: the two-map design is refused for them at these dates, passed as `date_a` and `date_b`, and another unlabelled map or inference cannot tell change from error; `two_map_design_across_dates`) and the one next step that applies (each map's own sample, labelled against a reference of its own date), and the first 10 differing windows inline with every one in a file (`differing_path`, named by a `list_file` fact); for grading, per-arm E-AURC / AUROC / capture with a head-to-head verdict and a per-group one-sided exact sign test; for estimation, a saved design, then the error rate with the interval valid at every sample size first, then the one that design earns (and per-class accuracy, and a certified zone for a random design; for a plan drawn with `seed_from_map`, the certified zone packed into olmoearth-inferencex's certificate, and its check against a copy of the map); for two maps of one time, the windows where they differ to label, then which map is more accurate by the exact sign test (or, past a fifth of the differing windows, the interval) and the difference in accuracy with its 95% interval.

**What.** The question a practitioner asks the moment a prediction map lands: *which windows do I open first, and how much of the error do I catch if I only open 5% of them?* Windows are ranked by the model's own **top-1 minus top-2 margin**, optionally boundary-first (the nine-level indicator: how many of the 8 neighbours were predicted as a different class). `olmoearth_grade_review_rule` (opt-in: it needs per-unit error labels a Studio user rarely has) is the honest-broker half — it scores *any* candidate suspicion signal against that margin baseline and a no-model control, with the group (scene / event / region) as the unit of replication, because units inside one scene are not independent. `olmoearth_review_budget_ceiling` is the arithmetic guard: no rule can catch more than `min(1, budget / error_rate)` of the errors, so a capture of 0.45 at a 10% budget with a 20% error rate is 90% of what was reachable, not "45%".

**Why.** Three reasons this is a skill rather than a helper. (1) **It is measured, not asserted.** On the tasks of Ai2's own published embedding suite the margin ranks errors better than a random order: its AUROC for errors is above 0.5 in all 3,560 cells of 16 encoders, OlmoEarth's four sizes among them, at ten probe seeds each (exp79), and with OlmoEarth Base, reviewing the 10% of units with the lowest margin finds a median 21.4% of the errors on the suite's 24 tasks, against 10% for a random 10%, and more than 10% on every task (exp70). Its lead over the suite's two no-model controls on 24 of 24 tasks (p = 6e-08) says little on its own: a red team of 30 September 2026 found those controls near chance there (the better of the two no better than a random order on 9 of the 24 tasks; the embedding-distance control below chance, AUROC under 0.5, on 21). Ensemble disagreement, cross-model disagreement, two-view disagreement and feature-space typicality were each measured against the margin on expert labels, and none ranked errors better. The record is [`2imi9/olmoearth_inferenceX-record`](https://github.com/2imi9/olmoearth_inferenceX-record) (`docs/claims.yaml`: `exp79-margin-beats-random-everywhere`, `suite-review-at-ten-percent`, `suite-controls-are-near-chance`). The tool states those verdicts in its result, scoped to the case at hand, so the agent cites evidence instead of asserting authority and does not widen it to cases no experiment grades. (2) **It closes a real gap.** Skill #9 answers *is this regime trustworthy*; nothing answered *which windows are wrong*. (3) **It is the cheap half.** #9's ensemble path costs grid² slow `pixel-value` calls per result and needs ≥2 distinct results; this needs one forward pass you already ran.

**Honest limits**, kept whole in the evidence file (`evidence_detail_path`) behind every result's `evidence_scope`: the evidence is for the OlmoEarth family at window level against seven references, not a general theorem; on one Sen1Floods11 flood event a no-model NDWI control matched confidence and beat it under v1.2; the margin only **ties** ensemble *predictive entropy* (the rejection is of the disagreement component, mutual information); a fitted readout that memorised its practice data degrades the ordering; and these numbers order a review well while being badly miscalibrated as probabilities — good for deciding what to look at first, poor for thresholding.

**Scores: brought, or read from a Studio result.** Studio exposes no logits (`StudioClient.pixel_value` returns each band's `raw_value` / `classification` only), and a margin cannot be recovered from a hard class. Pass scores from wherever inference ran — rslearn `model predict` (skill #17), an embeddings+probe pass (#3), any exported softmax. For a Studio result whose band is a `per_pixel_regression` score in `[0, 1]` of a two-class task, `olmoearth_review_set_from_result` samples the band on a grid (one `pixel-value` per window, no-data dropped and counted), reads each score `s` as `[1 - s, s]` and ranks with the same margin `|2s - 1|`, least decided first. It states the assumption in every result: the score is treated as P(positive) for ranking only, which needs no calibration, but the numbers are not probabilities of error. A regression band of any other range needs a decision `threshold`; a class map without top-k scores is refused, with where top-k scores come from (use #9 with two or more results). No coordinates are emitted — windows are `(row, col)` and index, and the locations a reviewer needs stay in the saved scores file — so rule §3.1 holds.

**A Studio class map with top-k scores.** A segmentation prediction submitted with `probability_output` (top_k of 2 or more; `olmoearth_submit_prediction`'s `probability_top_k`) carries, beside its class band `P`, each rank's softmax score (`P_rank1_prob`, `P_rank2_prob`, ...) and runner-up class as bands of their own, declared 0 to 254. `olmoearth_review_set_from_result` samples them on the same grid and ranks each window by its rank-1 minus rank-2 score (the uint8 levels' difference over 254; `score_kind` `topk_score`). Each window takes its rank-1 class, shown by its label. A window is valid by its rank-1 class band alone; one with a class but no score, or a rank-2 score above its rank-1, refuses the sampling. Every result states that the scores are Studio's uncalibrated softmax scores, quantized to 1/254, whose margin ranks windows and is no probability that the class is right; its evidence scope says no recorded experiment grades it, and it forbids `certification_guaranteed`. `olmoearth_plan_label_sample` takes every design for it (the reviewer writes the class seen), `olmoearth_estimate_map_error` gives per-class accuracy by class name, and `olmoearth_certify_zone` certifies a zone of a random design; `olmoearth_compare_review` refuses its scores file. In the first of two live runs on a kelp result (31 October 2026), the grid at its maximum, 16 x 16, held 7 valid windows: 189 points were no-data and 60 answered HTTP 404 not_found_error (where other points answered; which result file covers which point was not tested).

**A Studio result's own files.** `olmoearth_scores_from_studio` (`tools/studio_scores.py`, the `inferencex` extra) downloads a result's model output at native resolution (`GET /prediction-results/files`, one GeoTIFF per UTM zone, and a `README.md` for top-k scores) and reads a class map with top-k scores or a `[0, 1]` score band; the kind is decided from `result_metadata` before any download, and a class map without top-k scores, a top-1 result, a score in other units and another layout are refused. Each zone becomes a run directory under `<scores root>/studio_results/` (`scores.tif`, `manifest.json` with `source.kind` `studio_files`) and is pooled by `olmoearth_scores_from_file`'s own handler, so its scores file goes to the review set, the label plans (a `seed_from_map` plan included), the estimate and the certified zone. Each zone is its own map, and no tool combines zones. The decoding of top-k scores changes neither this route's window order (each window's mean rank-1 score) while no rank-1 score is raw 0, nor the grid route's margin. Studio's files README gives `(value - 1) / 254`, and the tool decodes with it. On the kelp result, measured on 31 October 2026, raw rank-1 plus rank-2 is 254 on every valid pixel, which only `raw / 254` reads as summing to 1, and rank-2 is raw 0, which that README calls unused, on 62% and 56% of the two zones' valid pixels; so `raw / 254` fits better. The result states such counts as facts. A `[0, 1]` score read as the probability of the positive class is an assumption, and the result says so. The zip is untrusted input (only the native GeoTIFFs and the README read, never extracted by name, stored or deflated only, the entry list (by the largest size any end record declares, ZIP64 ones included) and sizes capped, a native file opened only when its first bytes are a TIFF's and only by the GeoTIFF driver, so a VRT under that name reads no other file), and the download token reaches no result, manifest, error or log. In the second live run, on the same result, at patch 11, its two zones gave 2,468 and 2,837 valid windows, against 7 on the first run's grid; at patch 4, then the default, both zones held more windows than a ranking takes (200,000) and were refused for pooling; now, with no patch given, each zone takes the smallest side from 4 up whose windows a ranking takes, and a fact names it. Pooling counts a window when at least half its pixels are valid, and leaves out the pixels past the last whole window (`pixels_outside_window_grid`). A certificate on a zone binds the raster the agent decoded (`scores.tif`), not Studio's native file, which does not verify: the certificate names that raster (`map_bound`) and says so. Assumed and unverified: the README's layout for k above 2, that Studio's zips are stored or deflated, and the result's model as its prediction's `model_id`.

**Scores from a direct model run.** A model run outside Studio writes every pixel's pre-argmax scores, which Studio gives only as the top-k scores of a segmentation prediction submitted with `probability_output`. [`scripts/score_area.py`](https://github.com/2imi9/olmoearth_inferenceX-record/blob/main/scripts/score_area.py) in the companion package's research record runs Ai2's fine-tuned AWF model on a GPU cluster and writes a georeferenced `(C, H, W)` float32 `scores.tif` (logits or probabilities, NaN no-data) and a `manifest.json` (model and revision, classes, logits or probabilities, the software versions). `olmoearth_scores_from_file` reads such a directory under `OLMOEARTH_SCORES_ROOT` (the scores files' path rule: a symlink or a manifest pointing outside is refused, and the raster's sha256 must be the manifest's), pools it to windows with `oe_inferencex.review.assess.assess_prediction` exactly as `oe-inferencex assess` does (`is_logit` from the manifest, windows of `patch` pixels, a window valid when at least half its pixels are), and writes one scores file: each valid window's row holds the package's window confidence at its majority class and 0 elsewhere (exp64's mapping), with its pooled top-1 probability and class beside it. `olmoearth_review_set` on that file is the package's review set (the same windows in the same order; only exactly tied windows can be ordered differently), `olmoearth_plan_label_sample` draws what `oe-inferencex sample` draws, and two runs of the same area go to `olmoearth_compare_review`. A channel the manifest marks as the label fill value (`nodata_value_<c>`; AWF's channel 9, never a training target) is left out of the margin and the class vote unless `include_fill_class` is set, which ranks the served map over every channel. For logits the confidence is the top-1 minus top-2 logit margin; for probabilities it is the package's, the top-1 probability. The result names the model, its revision, the classes and the date window, never the area; each window's location stays in the file for the labelling sheet. The raster is read by the package's own reader, `oe_inferencex.common.raster.read_raster`; a file it cannot read (missing, or not a raster) is the tool's refusal, never an exit of the agent. Reading the GeoTIFF needs rasterio, which the `inferencex` extra brings (`olmoearth-inferencex[geo]` >= 1.20.3; an older release is refused with the upgrade line); without it the tool answers with the install line. The tool also reads what `oe-inferencex from-olmoearth DATASET --out RUN` writes from the rslearn dataset an OlmoEarth model run leaves (`rslearn model predict`, or `olmoearth_run`): `scores_<EPSG>.tif`, the softmax probabilities of every window on one grid per CRS, NaN where no window predicted, and `olmoearth_output.json`, the summary that names them. Pass RUN, the summary, or one `scores_<EPSG>.tif` when the run wrote one per CRS. The summary names no model, revision or classes, so the classes are named by channel, `class_0` to `class_{C-1}`, and the result says the model and revision are not named by the run's `olmoearth_output.json`. A run that wrote class ids only (rslearn's default output, which `from-olmoearth` refuses too) is refused with the package's words on how to get probabilities (`output_probs: true` in the segmentation task, a float32 output layer, the rerun) and the fine-tuned checkpoint; the rslearn dataset itself is refused with the `from-olmoearth` command that reads it, and a per-window classification (`window_probs.npy`) as having no grid to pool. Only a raster that resolves inside the scores root is opened to tell class ids apart (a link out of it is passed over), and a record that is not valid JSON is refused by name, with how to write it again.

**A certificate anyone holding the map can check.** A certified zone of a direct run's map can travel with the map as olmoearth-inferencex's certificate (`oe_inferencex.certify.certificate`): a STAC Item stating the guarantee, the zone as a GeoTIFF mask on the window grid, the labelled sample, its sidecar and the zone, and digests binding them to the map's pixels. Its verify builds the certificate again from the map, the bundled labels and the recorded settings. The route is file-based, so the agent drives the package's command line for the files a certificate rests on (this interpreter with `-P`, so the working folder is never on its import path; no shell; the agent's Studio and LLM keys left out of its environment; a time limit, off the event loop; a failure is the tool's refusal). `olmoearth_plan_label_sample` with `design='random'`, `seed_from_map` and `alpha` (and `delta`, `rule`) on a direct run's scores file (only the one `olmoearth_scores_from_file` wrote from a model run's output GeoTIFF; any other scores file, inline scores or a Studio result is refused, as the tool's description says) runs `oe-inferencex sample RASTER --design random --seed-from-map --alpha A` in a working folder under `<scores root>/certificates/`: the seed is 128 bits of sha256 over the map's digest and the draw's settings, alpha, delta and the rule included, so anyone holding the map draws the same windows. The agent's design is that draw, checked window by window (confidence and class) against the package's sheet; a scores file that left a label-fill channel out is refused, since a certificate is of the map over every channel. `alpha`, `delta` and `rule` given without `seed_from_map` are refused, as `oe-inferencex sample` refuses them without `--seed-from-map`. `olmoearth_certify_zone` on that plan keeps to its alpha, delta and rule, as `oe-inferencex certify` does. The labels first graded on the plan (by the estimate, the zone or the certificate) are written into the package's sheet and fixed there: other labels afterwards are refused, and so is drawing the same plan again over them, since a certificate cannot show labels were not changed after a result was seen. `olmoearth_write_certificate`, with the same labels and the map's date (by default the date window a `score_area.py` manifest records; a `from-olmoearth` run records none, so pass `date`), writes them into the package's sheet, runs `oe-inferencex certify`, checks that the package's certify and `olmoearth_certify_zone`'s computation agree on these labels (the same windows, not only the same count), and calls `certificate.build`, which verifies the bundle before it hands it over. It writes no certificate when no zone is certified (the labels are in the sheet and certify's zone file beside it all the same), and none over one already written for the plan: a certificate is written once. Its result carries the whole-map estimate from the labels, as the zone's does. `olmoearth_verify_certificate` calls `certificate.verify` against a copy of the map under the scores root, given as a plain GeoTIFF or `.npy` file (by its name and first bytes: GDAL would follow the paths inside a VRT) or as the scores file that names it, and says which checks pass. Checked against the map the certificate names (with no `map_path`, or a `map_path` that is that file, as a scores file of the issuer's run is), it says the check shows only that the two agree; a certificate that names its map outside the scores root, or by a relative path, needs `map_path`. With `window` `[row, col]`, never coordinates, it says whether that window is in the zone verify builds again (`certificate.point`). A certificate restates the zone: every result states the package's `ISSUED_NOTE` (what delta counts) and `ISSUERS_WORD` (the labels, the map's date and a single draw are the issuer's word). Both tools need nothing beyond the `inferencex` extra, so they are default tools.

**How wrong is the map (design-based estimation).** The review set is chosen to hold errors, so it is **not a sample**: labelling it and dividing overstates the error rate (1.8 to 5.8 times on the companion package's exp78), and the simple-random-sample interval `p ± 1.96 sqrt(p(1-p)/n)` does not apply to a stratified or targeted design, nor to a pool of both. Three tools wrap `oe_inferencex.estimate` from [`olmoearth-inferencex`](https://github.com/2imi9/olmoearth_inferenceX) >= 1.20.3, the optional `inferencex` extra (`pip install 'olmoearth-agent[inferencex]'`; it brings numpy, which the core package does not use; without it the tools say so and compute nothing): `olmoearth_plan_label_sample` draws the design (confidence strata with Neyman allocation by default, `random` when a certified zone is wanted) and saves it with a labelling sheet, every row of which the design file's routes need labelled (the fact names only the routes the plan has: the estimate always, the certified zone for a random design of a map with confidence, the certificate for a `seed_from_map` plan; a random sheet's first rows are a smaller random sample only as a fallback when labelling stops for a reason that does not depend on the labels read, never because of what they show, with none of the zone or certificate the full sheet gives: `prefix_is_random_sample`, and every plan forbids calling part of the sheet enough); a confidence or proportional plan lists its strata's sizes and labels (`strata_sizes`, `allocation`, with `strata_meaning`: the package's quantile strata of the margin, stratum 0 the least confident); `olmoearth_estimate_map_error` returns the error rate with the interval valid at every sample size first (`estimate_error_rate(valid=True)`, for every design of one map), then the interval the design earns and the package's `method`, each named (`intervals`), with the package's `VALID_NOTE` word for word: under the confidence and proportional designs the second is Wilson's on the design's effective sample size, which the package calls nominal (91.3% coverage at 100 labels on a 200-window map, exp105), never exact; under a random sample it is the same exact interval; the answer must state the valid interval and the design (`must_state`). Per-class user's/producer's accuracy with reference classes comes the same way (`estimate_per_class(valid=True)`): the `weakest_classes` ranking carries each class's producer's accuracy and `drawn` flag beside its user's accuracy, and the `user_vs_producer` fact names, from the package's rows only, each class whose user's and producer's accuracy intervals do not overlap and each class the map draws too little or too much (read on the exact interval that holds for all classes together where the random or class design gives one; the valid intervals hold each on its own, not jointly, and the fact says so; where the valid intervals were not computed, the design's are named, nominal under the confidence and proportional designs); a class whose producer's-accuracy interval lies wholly below its user's is a `must_state` (at most two, one on a Studio result, after the valid interval), written from the producer's side only (the share of the class's ground the map finds, and that it misses the rest), so an answer that gives only the user's accuracy does not satisfy it. On a class map, `user_vs_producer` and its `must_state` name each class as the map writes it, with the agent's internal code as `code`; the `weakest_classes` sentence still names a class by that code, with the written class beside its count. For windows labelled without a design, the tool checks they could be a random sample first (a review set is refused) and gives the one interval they would earn as one; `olmoearth_certify_zone` returns the largest most-confident share whose error rate is at most `alpha`, random designs only, and a certified zone's `meaning` ends with the package's `ISSUED_NOTE` word for word, which says that delta counts all samples, those that certify nothing included, and that among the samples that do certify a zone the share wrong can be larger (most of all when the zone's true error rate is just above `alpha`), so a certified zone is not a 1 - delta chance of being right. When it certifies nothing, its `whole_map_estimate` says that rate describes the whole map, not its most confident part, and names the smallest zone tested with its coverage, labels and wrong count, as the result gives them (`whole_map_rate_for_a_zone` forbids explaining the outcome by the whole-map rate against alpha). `olmoearth_compare_review` also takes `date_a` / `date_b` / `labels_date` and, with the extra, attaches the package's reading of what a difference means across dates.

**A Studio class map without top-k scores.** A classification result without top-k scores gives each window's class and no probability, so nothing ranks its windows: it gets no review set and no certified zone, and the review set, `olmoearth_certify_zone` and the ranking designs refuse it in one sentence (`zone_for_a_class_map` forbids offering a zone of it; in a run that also holds a map with scores, the answer check reads only a clause that names the class map, by its kind or its result id). Labels still measure it, over the result's sampled grid points (at most 16 x 16, one pixel each), not every pixel. `olmoearth_plan_label_sample` with `design='random'`, or `design='class'` (the class design of Olofsson et al. 2014: strata by map class, at least `min_per_class` labels each (50 by default), or all its windows if it has fewer, the rest by class size; its result lists each stratum's class as the map writes it (with the agent's internal `code`), windows and labels as `per_stratum`, since the strata are the classes the map holds, in order, and stratum h need not be class h), reads each window's class as the two-map design does and gives olmoearth-inferencex's label budgets: `plan.plan_error_rate`, the random labels for a whole-map interval no wider than a stated `width` (0.10 by default; at 50% wrong unless `expected_error_rate` is given), and `plan.plan_class` for a stated `class_share`: the random labels that flag a class of that share drawn by the map at half of it, all classes' intervals together at 95% (not a per-class accuracy budget). Both plan a random sample, not the class design. The reviewer writes the class seen in each window (blind under the class design: map_class and stratum hidden, the rows shown shuffled, as the package's `CLASS_BLIND_NOTE` says). `olmoearth_estimate_map_error` reports, as for a map with scores, the interval valid at every sample size first (`estimate_error_rate(valid=True)`), then the design's own (under the random design the same exact interval; under the class design, of a class map or of a map with scores, the union bound over the classes, which covers at least 95% too), and each class's accuracy the same way (`estimate_per_class(valid=True)`), with the package's notes word for word; the answer must state the valid interval and the design (`must_state`). On the sheet, a `reference_class` filled on some windows only is refused, and a `wrong` filled beside a full `reference_class` must agree with it.

**Which of two maps is more accurate (the two-map design).** Where two maps of the same windows at the same time give the same class, both are right or both are wrong, so their accuracies differ only through the windows where they differ, and labels there say which map is more accurate with far fewer labels than a sample of the whole map. No score is needed, so a Studio class map gets it. `olmoearth_plan_label_sample` with `design='disagreement'` takes two Studio results of the same area (`result_id` for map a, `result_id_b` for map b; sampled on one grid by `olmoearth_compare_results`' own pair sampler, at most 12 points a side, no-data dropped; a classification band read as its class, a `[0, 1]` score cut at 0.5 and any other regression band only with a `threshold`) or two scores files of one window grid (`scores_path`, `scores_path_b`; each window's `map_class`). It reads the dates the maps describe (a Studio prediction's start and end times, else `date_a` / `date_b`) with `oe_inferencex.compare.dates_reading` and refuses maps of different or overlapping times, or with one date only, stating the package's reading: across dates a window where the maps differ can be a change on the ground, and labels seen at one date grade both maps against it. Maps that never differ are refused in the package's words. It then draws the windows to label at random among those where the maps differ (`estimate.sample_disagreement`, with its `seed`), lists them by index and `(row, col)` with both maps' classes (locations only in the labelling sheet), gives the windows compared (N) and differing (D), and `plan.plan_which_map`'s budget advice for a stated `difference` in accuracy (0.05 unless given; the `which_map_budget` fact). The reviewer writes the class seen in each window, or `?` where it cannot be judged. `olmoearth_estimate_map_error` on that design (`reference`, or the sheet's `reference_class`) grades it with `estimate.compare_from_disagreement`: which map is more accurate, or neither (`which_map`), by the exact sign test while the labels are at most a fifth of the differing windows and by the interval past that (`verdict_rule`; the sign test's own sentence in `sign_test_statement`), the 95% interval on the difference in accuracy, a minus b, over the N windows, the counts (right in a, right in b, in neither, not judged) and the package's notes word for word (`note`, `verdict_note`, `method`). Every number is the package's. The result's contract requires the answer to state the test or interval and the number of labels (`must_state`, and the `which_map` fact) and forbids naming a map the grading does not name (`more_accurate_without_its_test`); the plan, which holds no labels, forbids naming any (`winner_without_labels`). The answer check reads a map named by its letter (map a / map b, in either case); "the OlmoEarth result is more accurate" is not read. A reference class neither map writes is right in neither and counted in the `references_outside_the_maps_classes` fact; references that all lie outside the maps' classes are refused. Two scores files must share their grid's shape and, where both locate a window, its centre. It says which map is better, not either map's accuracy, and `olmoearth_certify_zone` refuses the design.

**Tools composed.**
- `olmoearth_review_set` (scores → the ordered review set at a budget, confidence or boundary-first), `olmoearth_review_set_from_result` (a Studio result's `[0, 1]` score, or a class map's top-k scores → the same ranking), `olmoearth_compare_review` (two inferences of the same windows; the side question declined), `olmoearth_grade_review_rule` (opt-in; candidate vs margin vs no-model control, with a per-group sign test), `olmoearth_review_budget_ceiling` (`min(1, budget/error_rate)`, and what share of it a quoted capture reached).
- `olmoearth_scores_from_file` (`tools/scores_file.py`, the `inferencex` extra): a direct model run's scores raster and manifest, or `from-olmoearth`'s `scores_<EPSG>.tif` and `olmoearth_output.json` → the scores file the tools above and below read.
- `olmoearth_scores_from_studio` (`tools/studio_scores.py`, the `inferencex` extra): a Studio result's native-resolution files (a class map with top-k scores, or a `[0, 1]` score band) → one run directory and scores file per UTM zone, pooled by `olmoearth_scores_from_file`'s handler.
- `olmoearth_write_certificate`, `olmoearth_verify_certificate` (`tools/certificate.py`, the `inferencex` extra): a certified zone of a plan drawn with `seed_from_map` → olmoearth-inferencex's certificate, and its check against a copy of the map (`certify.certificate.build`, `verify`, `point`; `sample` and `certify` through the command line).
- `olmoearth_plan_label_sample`, `olmoearth_estimate_map_error`, `olmoearth_certify_zone` (`tools/estimation.py`, the `inferencex` extra); with `design='disagreement'`, the two-map design and its grade (`estimate.sample_disagreement`, `estimate.compare_from_disagreement`, `plan.plan_which_map`, `compare.dates_reading`).
- Logic in `analysis/review_set.py`: pure-Python ports of `oe_inferencex.common.metrics` (`aurc_expected`, `oracle_aurc`, `excess_aurc`, tie-aware `capture_at_budget`, `auroc`), verified against the numpy originals to < 1e-9 over 400 randomised cases including heavy ties and degenerate inputs. Tie handling is by expectation under random tie-breaking, so no result depends on raster order — which matters because the boundary indicator has only nine levels.

## Adding a skill

A new skill is one PR with:
1. For an instruction skill, a folder under `src/olmoearth_agent/skills/packages/<skill-name>/` containing `SKILL.md` + optional `scripts/`, `references/`, `assets/`; it ships in the wheel and `SkillLoader` discovers it (`tests/skills/test_packaging.py`).
2. Any new global tools added to `PLAN.md` §1.
3. A `tests/skills/test_<skill_name>.py` exercising the skill end-to-end against the live Studio API (mark with `@pytest.mark.integration`).
4. An entry in this `SKILLS.md` matching the per-skill template above.
5. A `CHANGELOG.md` line under `### Added`.

See [`CONTRIBUTING.md` §3](CONTRIBUTING.md#3-branch-and-pr-workflow) for branch naming.
